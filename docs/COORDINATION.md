# Coordination

How the agents working on Dark Territory stay out of each other's way. Read this before starting work. Change it in the
same PR as the work it describes, or in a small PR of its own when you only claim or release an item. **This file is the
source of truth for who owns what**; chat with one session isn't seen by the others.

## The rules

1. **Claim before you start.** Take your numbers first (*Taking numbers* below: a queue number and a note number, which
   nobody else can then take). Then put your name (below) and a branch against the item in the queue, and land that change
   on main first: a docs-only PR, merged as soon as it's green. If someone else's name is already there, pick another item or
   ask on their PR.
2. **One item, one branch, one PR into main.** Squash-merge when CI is green (`dotnet format` clean, build, all tests).
   Merge main into your branch rather than rebasing a branch someone else may have checked out.
3. **Your ARCHITECTURE §8 note is a file of its own**, `docs/notes/<number>.md`, with the note number you took (note 521).
   §8 in ARCHITECTURE.md is the notes' index (`tools/coord/notes.py index` writes it). Read the notes your work touches,
   not the whole of §8.
4. **Done means merged.** Set the item's row to done, with its PR link and note number, in the PR that lands it. Done and
   dropped rows are moved out of the queue into [docs/COORDINATION-ARCHIVE.md](COORDINATION-ARCHIVE.md) (the director, 18 Oct);
   look a finished item up there.
5. **Questions between agents go in PR comments** on the PR in question (both sides are watching their own PRs).
   Questions for the director go in the Director's Inbox (*The director's inbox* below), with a line in *Waiting on the
   director* for agents that can't open it, and to the director in your own chat.
6. **Merging main into your branch** (note 521): this file, ARCHITECTURE.md and the logs merge on their own (both sides kept;
   `.gitattributes`). The Coordination check on your pull request (`python3 tools/coord/check.py`) says if your claim's queue
   or note number was taken meanwhile; take the next free ones (`tools/coord/check.py --next`) and say so in your log.
7. **Log what you do** in your own file, `docs/log/<agent id>.md`, every entry with its UTC date and time (format in
   docs/log/README.md). Give yourself an agent id when you start (the table below).
8. **Follow CLAUDE.md.** Design numbers in `content/tuning`, a deterministic Sim, everything verifiable headless, visual
   changes looked at.
9. **Leave your work where another agent can pick it up** (the director, 13 Oct 2026: "Make sure your delegates are
   posting their work in the coordinator md so that if we run out of tokens here other agents can pick it up"). For every
   item you hold: push your branch at each working step, even WIP, and name it in the item's queue row; keep a
   **Handoff** block in its note (`docs/notes/<n>.md`) current on main: what's done (commits, PRs), what's left in order,
   what you found (causes, seeds, the commands that reproduce it), open questions; and keep the row's status true
   (claimed, in progress, in review with its PR, done, dropped and why). Land those docs updates on main promptly, as
   small docs PRs: a note only on your branch helps nobody once your session ends. An item whose session is gone is
   anyone's to carry on from its handoff, saying so in its row and their log.
10. **A protocol bump takes main's version + 1 when it merges, not when it branches** (D1, 13 Oct 2026: three PRs took
   55 at once). `Messages.Version` (`src/DarkTerritory.Sim/Net/Messages.cs`) can merge cleanly with a stale number. Right
   before you merge, re-read main's, set yours to one past it, fix the tests that pin it, and re-run the netcode tests on
   the merge. Two wire formats must never share a number.
11. **Usage limits** (the director, 15 Oct 2026): when a session named "Token Budget Manager" messages you, do what it asks
   and reply to confirm (*Accounts and usage limits* below). A handoff is rule 9's Handoff block, in that section's shape.

- **State:** ACTIVE (working); PAUSED until *time* (the 5-hour limit: its sessions are waiting with their work intact, so
  its items aren't abandoned: don't take them); LIMITED until *weekly reset* (the weekly limit: its items are handed off).
  Each account edits only its own row: its Token Budget Manager updates it **every hour from 6 am to 9 pm Montreal** (the director, 16 Oct: "It's very important that you know where each other is at"; a session's rate-limit events carry the numbers). This file merges as a union, so a
  merge can leave two rows for one account: keep the one with the later *Updated*.
- **Items stay in the queue.** There's no second task list: an item's queue row is its task row (rule 9). When an account is
  paused, its rows say `paused (account limit, back <time UTC>)`. When it hands off, they say `open for pick-up` with a
  link to the handoff, as #529 and #530 do.
- **A handoff** is the Handoff block in the item's note (`docs/notes/<n>.md`, rule 9), or a `docs/handoff/<agent>/` README
  when it covers several items. It's on main, with the branch pushed, and detailed enough for a fresh session with none of
  your context:
  - From: account and agent id, time (UTC), reason (e.g. "weekly at 93%")
  - Branch and last commit (pushed)
  - Goal
  - Done so far (commits, PRs)
  - Next steps, in order
  - Decisions made and why
  - Gotchas and open questions
  - Files touched
  - How to verify (the commands)
  - Claimed by: — (whoever picks it up writes their account, agent id and the time here, and their name in the row)
- **Picking up:** an account under 60% of its weekly limit may take the oldest `open for pick-up` item. Claim it in the row
  and in the handoff's *Claimed by*, in a docs PR that merges first (rule 1).
- **When the Token Budget Manager messages you** (sessions on its own account): at **checkpoint**, commit and push your WIP
  and bring your row and handoff block up to date. At **prepare handoff**, finish the small step you're on, push, and write
  the handoff. At **execute handoff**, start nothing new, land the handoff on main and set your rows to `open for pick-up`.
  At **pause**, stop at a clean point and wait for the reset; don't hand off. Reply to confirm each time.

## Taking numbers (note 521)

A queue number and an ARCHITECTURE §8 note number are taken on the repository's `claims` branch: a file per number,
`queue/<n>.json` and `note/<n>.json`. GitHub won't make a file that's already there, so whoever makes a number's file
first has it. Two agents reaching for the same number can't both get it, and the second learns that at once, before any
work.

- **With a token** (`GITHUB_TOKEN`, `GH_TOKEN` or `gh`): `tools/coord/claim.py --agent <id> --title "<the item>" [--notes 2]`
  prints the numbers it took.
- **With your GitHub tools** (a cloud session without a token):
  1. List `queue/` and `note/` on branch `claims` (get the contents of a path, ref `claims`).
  2. Take one more than the highest there and in this file (`python3 tools/coord/check.py --next`).
  3. Create `queue/<n>.json` on branch `claims` with `{"agent": "<id>", "title": "<the item>", "at": "<UTC>"}`, and no
     `sha`. If GitHub says the file exists, someone took that number a moment ago: try the next one. (No `claims` branch
     yet: `claim.py` starts it as an orphan; with the GitHub tools, make it from main first.)
  4. Do the same under `note/`.
- **Then write your queue row** with those numbers, as before. The Coordination check fails a row whose number another
  agent claimed. After each merge, the check runs on main too: when two PRs land the same number, the one that landed
  second gets a comment.
- The holdings below were written by hand before the claims branch. They stay as the record, but nothing is added to them
  any more.
