531. **Bots gone at the start of a night (queue #268, D1; the director, 9 Oct 2026, testing main's build: "I tried to play with bots and they were all dead when we spawned in").** Reproduced headless: the app, `--route frontier:7 --bots 3`.
   - **What happened.** The bots joined (ids 1-3; `NetPlaySession.Start` steps the host and each bot until it's in). Then the night's scene loaded before the first frame, about 40 s on the software renderer here, with nothing polled: not the host, not the bots. On the first frame `BotCrew.Step` runs before the host's step. Each bot's transport polled first, found nothing from the host for 40 s (over `DatagramOptions.TimeoutSeconds`, 8), and dropped the link, so the bots were gone from the crew before anyone saw them. A friend already connected when the host stood that long would have been dropped the same way.
   - **Now** `DatagramTransport.Poll` knows when it was last polled. A poll long after the last one (over twice the keepalive, or half the timeout) means this process stood still, so that time is nobody's silence: every link's last-heard moves on by it. A peer that really has gone still still times out, the usual 8 s after.
   - **Verified.**
     - `UdpTransportTests.AWholeProcessStandingStillDropsNobody`: a host and a client in one process, both unpolled for longer than the timeout, the client polled first. Both links live on. It fails without the fix.
     - `ASilentPeerTimesOut` still holds: a client that stops while the host keeps polling is dropped.
     - The app with 3 bots: all three connected and alive, the driver in the cab, under way.
     - Ballast.Net 18/18, Ballast.Online 13/13, the Sim's netcode/rejoin/lobby classes 24/24, the 28 Game classes that use the net sessions 170/170.
