514. **Developer builds and player builds (W1, queue #251; the director, 9 Oct 2026: "We need a way for these developer features to not ship in the final build as well").** The developer tools that come with queue #252–#262 (recording and replaying nights, feedback from inside the game, live control) are for the director's test builds and the agents, never for players. They're kept out of a player's build by how it's compiled, not by a setting that could be left on.
    - **Two assemblies that never ship:** `Ballast.Dev` (the engine's developer tools, game-agnostic) and `DarkTerritory.Dev` (the game's). Each marks itself `[assembly: AssemblyMetadata("DevTools", "true")]`. `dt` references them (it never ships), and so do their tests (`tests/DarkTerritory.Dev.Tests`).
    - **One switch, `DevTools`** (Directory.Build.props, true unless set): with it on, the app references `DarkTerritory.Dev`, defines `DEVTOOLS` and marks itself too. It reaches the tools only under `#if DEVTOOLS` (`var dev = DevTools.Start(args)` at launch, then `dev.…` at the hooks), so with it off the app's code has no trace of them. The libraries a player's build is made of (Ballast.*, DarkTerritory.Sim, .Game) never reference them, so they compile the same either way, and a switch between the two rebuilds only the app.
    - **Packaging:** `tools/package.sh` builds a player's build with `-p:DevTools=false` (`DarkTerritory-<rid>`), and `--dev` builds the director's (`DarkTerritory-Dev-<rid>`, a folder `upload.sh` never sends). The Test build workflow makes the dev one unless `player` is ticked; CI's package job and Release make players'.
    - **Proved of every package:** `dt build check <folder>` (`PlayerBuild.Check`) reads every assembly's metadata and fails the folder for a dev assembly by name, any assembly referencing one, any assembly bearing the mark (a dev assembly renamed is still caught), or a .deps.json listing one; `--dev` checks the other way (the app marked, `DarkTerritory.Dev` beside it). package.sh runs it on every package it makes, and upload.sh again on each build just before a store gets it.
    - **Seen:** a dev build draws `DEV <commit>` small and dim in the top right over the menus and the HUD, so the director (and anyone shown a screenshot) knows which they're looking at; `--no-dev-mark` hides it for footage. A player's build draws nothing there.
    - **Rules for the next dev tool:** put it in `DarkTerritory.Dev` (or `Ballast.Dev` when it's the engine's), reach it from the app only under `#if DEVTOOLS`, never with an `#else` (that's what players would run instead: write it outside the `#if`), and never reference a dev assembly from a library that ships. `PlayerBuildTests` fails the build on any of these.
