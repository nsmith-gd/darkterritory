695. **A top-to-bottom performance audit (A1, queue #427; the director, 13 Oct evening, `docs/playtest/2026-10-13-evening.md` lines 1–3).**
"We're definitely running into some sort of performance problem here. So I think we're going to need a performance audit
of everything"; "now that we're getting back to the town, things are starting to stutter again"; "I'm getting a frame
drop when the UI pops up" (the talk prompt near townsfolk); "I'm also getting frame drops when I'm rapidly turning". The
director, 13 Oct, on main: "things were pretty small once we left the towns, but the towns feel like they're just
crawling ... really bad performance drops in there." The director asked A1 for the whole audit, top to bottom.

   - **How it's measured.** The app runs headless in the town (`xvfb-run ... DarkTerritory.App -- --route frontier:7 --internal 320x180 --window 320x180 --quit-after 45 --mute`). Note 691's report gives each part of the frame its ms and MB, the scene's own parts among them, with the counts on its slow-frame lines. On this machine the render runs in software (lavapipe) and its time means nothing. The CPU's parts are the game's own code, and on any machine they cost the same proportion of the frame.
   - **Found 1, the town crawl (lines 1 and 3):**
     - Standing in frontier:7's first town, every frame allocated 10.8 MB. 10.1 MB of it was `scene: town houses`, which took 8 ms. The slow-frame lines said "house meshes built 27, meshes uploaded 27", every frame.
     - Why: `WorldArt.Houses` kept one cache of house meshes and let it go whenever a different town's houses were asked for. The terminus's town (note 600) is asked for its houses every frame, kilometres off or not, so the two towns emptied each other's cache every frame. The near houses (built to their designs, each its own mesh) were built again and uploaded on every frame in a town. On the line no houses are near, so nothing was rebuilt: "things were pretty small once we left the towns".
     - At 60 fps that's 600 MB a second of garbage, and the collector's pauses on top of it are the stutters.
     - **Mended:** each town keeps its own houses (`WorldArt.TownHouses`, the last `TownsKept` = 3 towns), and its blocks with them.
     - **After:** 0.6 MB a frame (0.4 MB of it this machine's 8 sim ticks a frame), the houses' part under 0.5 ms, hud/upload 8 ms down to 3.5 ms.
     - **Held by** `FogLoadingTests.ATownsHousesAreBuiltOnceNotEveryFrame`: frontier:7's first town with its terminus town, from the square and the houses, builds its houses once. It fails on the old cache.

   - **Found 2, code compiled on the spot (line 1's "a frame drop when the UI pops up", line 3's loading drops):**
     - A build wasn't ReadyToRun, so the first time any code ran in a night (the first prompt or card, the first creature, the first menu), .NET compiled it right then, in that frame. Each frame now counts the main thread's compiling (`JitInfo`, "jit N ms" with the methods), on its hitch and its slow-frame line.
     - frontier:7's start, from a release build, compiled 819 ms on the first frame (3,948 methods) and 204 ms on the second.
     - The prompt and card themselves cost little: next to a townsperson the HUD, the prompt and the talk take 0.5–0.7 ms and 19 KB, the same as anywhere. A first one compiled its code, and in a town the frame also rebuilt the houses (found 1).
     - **Mended:** `tools/package.sh` publishes ReadyToRun. The same start compiles 154 ms (1,489 methods) on the first frame and 1 ms on the second. That's 16 MB more on a 500 MB build. A precompiled dev build passes `dt build check --dev`.
   - **The collector's mode:** the app plays in `GCLatencyMode.SustainedLowLatency`, so no blocking full collection unless memory runs short. The background collector works alongside the frames.
