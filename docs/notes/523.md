523. **Tonight's build and the trends: main with the green pull requests on top, and the numbers per commit (W1, queue #260; D1 did both by hand: integration branches through the Test build workflow for the director, and "4-bot full nights with upkeep (frontier:7, 2700 s, seeds 1-3)" after merges).** A test build was main plus whatever D1 merged on top that day, and a night's numbers were whatever D1 measured last ("211 km on the director's 2:30 pm build, 140 on main last night, 155 now"). Both now happen on their own, beside D1's judgment, not instead of it.
    - **Tonight's build** (`.github/workflows/tonight.yml`, `tools/tonight/integrate.py`), every night at 7:30 pm Montreal time (the director, 9 Oct 2026, in the inbox; the schedule's two UTC times, 23:30 and 00:30, cover summer and winter time, and a first job lets through only the one in Montreal's 7 pm hour) and by hand:
        - **What it merges:** every open pull request against main that isn't a draft, whose head's checks are all green and that merges cleanly, onto main in number order. Green means every check run success, neutral or skipped, and every status success; none at all isn't green (GitHub runs no CI on a pull request in conflict). The pull requests and checks are read over REST (`gh api`): the cloud sessions' proxy refuses GraphQL.
        - **What it leaves out, and why:** "conflicts with main in …", or "merges onto main alone, but conflicts with #N merged before it, in …" (`git merge-tree` against main alone, and the files each earlier merge touched); red, still running, draft, another base, and a head that moved since its checks were read.
        - **The build:** `dotnet build Ballast.slnx -c Release`, `tools/package.sh --dev win-x64`, `dt build check … --dev`, and the zip uploaded as the run's artifact with TEST-PLAN.md and tonight.json in it. The merge is force-pushed to `tonight`, so anyone can reproduce it.
    - **The test plan:** each merged pull request's title, link, branch and head, and its "how to check" lines, then what was left out and why; in the zip and the job summary. The lines come from every section whose heading starts Verified, How to check/test, Test plan, Testing, Tests, Checks or Local checks (a `##` heading, a bold line, or a bold label like "**Tests:** …"), to the next heading of its level; else the body's first paragraph. The agents' footers are left out. There's no pull request template: these are the shapes the repository's bodies have (read from #2 and #569–#689).
    - **The trends** (`dt trends`, `DarkTerritory.Dev/Trends`, `.github/workflows/trends.yml`), on every push to main that isn't docs-only:
        - **The nights:** `dt trends measure --perf` measures `dt harness --route frontier:7 --bots 4 --cars 10 --enemies --upkeep --seconds 2700`, seeds 1–8 (D1's nights; eight fill two rounds of four cores), and `dt perf --frames 6` once. The CLI hands in its own `RunHarness`, so these are `dt harness`'s nights, not a copy, and their metrics are read from the report's JSON, as the bisect reads an older build's. Four run at once: each is its own host and loopback, and the numbers are the same one at a time or side by side (checked).
        - **The line:** one JSON object a commit: its subject and pull request, the time, the nights, each metric's mean over the seeds and each seed's own.
        - **The metrics:** `balance.*` (km, delivered, the run's deaths (App. D.9: every death in the night, not who's dead at the end), cars lost and delivered, cargo, net, crew home, grabs, rescues, fairness violations, pack fires, hot boxes caught, couplings parted); `pacing.*` (beats a minute, the longest quiet, quiets over 30 s); `net.*` (kbit/s down and up, the worst correction); `sim.cpuMsPerTick`; `perf.{pc,vr}.*` (each view's triangles and draws, the worst view's CPU ms, the build, prepare and record phases; not the GPU passes, which on lavapipe rank the passes and aren't a GPU's); and `moments.*`, #256's (note 519), once the harness report has a `moments` object. A metric a report lacks is absent, never a zero, and skipped.
    - **Falls** (`tools/trends/metrics.json`: the tool's thresholds, set by the noise, kept beside the tool; not design numbers): a metric's band is max(abs, rel × level) about the median of the five lines before it. A step past the band the bad way, from a line that wasn't past it, is a fall (a metric that stays down falls once); the good way is a rise. Lines measured on other nights start a series of their own. The km band, 15 %, is about twice the noise: on note 511's six seeds one change moved a seed's km about 4 km, so the mean of eight moves about 1.4 km of some 19. The counts (triangles, draws, bandwidth) are the same on every run of a commit, so their bands are tight (10 %).
    - **The record:** one run at a time, never cancelled; GitHub keeps one run waiting per group, so when main moves faster than a run (about 17 minutes) the newer push takes the waiting run's place and its line covers the commits between. The line goes onto `trends/main.jsonl` on the `trends` branch, a history of its own (`tools/trends/append.sh` writes the blob, tree and commit without a checkout; a push that loses a race reads the branch again and retries). The summary has each metric's last ten values, falls bold. A fall is commented on its pull request (the subject's "(#NNN)" or "Merge pull request #NNN"): the level, the last value, the new one, the band, each seed's, how to run a night again, and the bisect to run.
    - **The bisect** (`tools/trends/bisect.sh --metric km --good A --bad B [--from main.jsonl]`): `git bisect run --first-parent` in a worktree of its own; each commit built and measured with its own `dt harness` (and `dt perf` for a perf metric), so commits from before `dt trends` measure as well as new ones; this checkout's `dt trends judge` calls each bad on the bad end's side of the midpoint of the two ends' values. A commit that doesn't build, or whose night fails, is skipped.
    - **Measured:** a full night (seed 1, Release) 209 s here at load 4–6, one thread, about 290 MB, to dawn: 13.44 km, 1 death, no cars lost. `dt perf` 248 s at 12 frames on lavapipe, 122 s at 2 (the warm-up is most of it), so about 3 minutes at 6.
