535. **Note 450's "not yet": a lobby changed once it's open, a guesser slowed, a crew's record listed (B3, queue #275; netcode-audit.md gap 7).**
Note 450 left three things undone. A host couldn't change the password or the mood once the lobby was open: both were set
when the run was hosted. A password guesser wasn't slowed beyond each guess being a new connection and a refusal. And "the
longest runs they can" (the director's "Feeling Competitive") was only what the host said of the run: nothing listed a
crew's record distance beside it.
    - **A guess costs time.** A private run's wrong password is no longer refused at once.
        - The refusal is held back by `crew.guessDelaySeconds` (1 s). Each wrong guess after that from the same place waits
          `crew.guessGrowth` (2) times longer, up to `crew.guessDelayMaxSeconds` (30 s). A place with no wrong guess for
          `crew.guessForgetSeconds` (300 s) starts again from the first. All four are in player.json `crew`.
        - "The same place" is `HostSession.Origin`. `NetPlaySession.OriginOf` reads it through `HostGroup.Route` and each
          transport's `TryGetAddress`: the machine's address on the network (not its port, since a joiner's game dials from
          a new one each time), or `account:<id>` on the platform. A link whose origin can't be told is its own.
        - A place's guesses are judged one at a time. A new joiner waits in the greeting line while a wrong guess from where it
          came from is still held (`WaitsItsTurn`), so opening many connections at once gains nothing. The right password
          behind three wrong ones is let in only after their 1 + 2 + 4 s.
        - Nothing else is held up:
            - the right password on its first try;
            - a held place's token (note 253);
            - a friend the host trusts (note 450's `Trusted`);
            - another machine.
        - A guesser who hangs up on a held refusal changes nothing: its place still waits the delay out.
        - The waiting link takes no place, as before (note 254). A mistype costs a second; a guesser gets a few tries a minute.
    - **Changed with the lobby open.** The host of a listed run has three new rows on the in-night menu (note 292), after
      SETTINGS:
        - **MOOD**: left and right step it from the run's own.
        - **PASSWORD**: SET or NONE, never the words, since a host's screen may be streamed. Enter types a new one from blank;
          Enter again locks the run with it, and Esc keeps the old.
        - **OPEN THE RUN**: shown while locked; it takes the lock off.
        - The footer names LEFT/RIGHT, and while typing says "[ENTER] LOCK [ESC] KEEP THE OLD".
        - A joiner, and a run nobody finds on a list, have none of these rows. `NightMenu.Lobby` (`HostLobby`) is set only for
          a host with `Listed`.
    - **How a change reaches the run.**
        - Each row writes the settings (`Mood`, `LobbyPassword`, `PublicLobby`), so the next night from the town is hosted
          the same way.
        - Once typing's done, the app hands the run only what changed since the night began: `NetPlaySession.ChangeMood`,
          `ChangePassword`. A password given on the command line isn't undone by a new mood.
        - `ChangeMood` sets the platform lobby's `mood` at once; the LAN beacon carries it from its next call (once a second).
        - `ChangePassword` sets `HostSession.PasswordKey` and the lobby's `locked`. Whoever's aboard stays, and a dropped
          crewmate's held place still takes them back.
        - The words still go nowhere: the host keeps the key only, as at hosting.
        - Locking the run takes the crew's vote to put someone off away, and opening it gives it back (note 724: a public
          lobby is a listed one with no password); `ChangePassword` sets `HostSession.VoteKicks`, which the host checks every
          vote against. A joiner already aboard keeps the roster's VOTE as it was given at joining, so a vote they call on a run
          since locked is refused by the host.
    - **The crew going on keeps up (protocol 63).** A crew following its host to the next night (note 606) dialled with the
      key they joined with, so a password changed in the night would have locked them out. `CarryOn` now carries the run's
      key as it is when the host goes on: after the town, a flag byte and the key. `ClientSession.CarryKey` holds it, and
      `GoingOn` dials with it. A friend let in without a password is given the key too; they're the host's crew already.
    - **The record.**
        - A campaign night's distance is kept in its `RunLog` (`Km`, from `RunReport.DistanceKm`; a save from before reads
          none). The crew's distance, `Campaign.Distance`, is every night's together.
        - After each settled night the player's profile keeps the furthest any of their crews has gone (`PlayerProfile.Reach`,
          `RecordKm`).
        - A run they host is listed with it:
            - the platform lobby's `record` (whole km; "" for none);
            - the LAN beacon's fourteenth field (`LanAdvert.Record`, `LanGame.Record`; an older beacon reads none);
            - `ListedGame.RecordKm`.
        - The join list has a RECORD column beside MOOD ("1873 KM", "-" for none). For its room the name column keeps to a
          name's 24 letters, and TIER widened by one so DEEP TERRITORY no longer runs into the mood.
        - The PROFILE page says it over the tally: "RECORD: 212 KM, THE FURTHEST A CREW OF YOURS HAS GONE".
        - It's the host's record, not tonight's: what a player feeling competitive is choosing between is how far a host's
          crews go.
